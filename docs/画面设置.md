# iOS 游戏画面设置

在系统“设置 → App → 游戏”中修改。偏好按 App 保存，修改后需从 App 切换器关闭游戏并重新打开。

保存的画面偏好若已失效或类型不正确，启动时会用带【红】的日志记录键、原值和默认值，清除该项保存值并采用默认值。显式启动环境变量仍优先；其他启动错误仍直接报错。

| 选项 | 档位 | 默认 |
|---|---|---|
| 渲染分辨率倍率 | 0.5×、0.75×、1×、1.5×、2× | 1× |
| 抗锯齿 | 关闭、SMAA 中、SMAA 高 | 关闭 |
| 画面缩放滤镜 | 双线性、最近邻 | 双线性 |
| 帧率上限 | 30、60、120 帧/秒、不限 | 不限 |

倍率相对于游戏当前渲染尺寸。例如 1280×720 的可缩放目标在 2× 时约为 2560×1440；游戏动态分辨率仍然生效。沿用 Ryujinx 的纹理缩放限制，不能缩放的目标保持原尺寸。2× 的相关目标像素数约为四倍，内存占用与图形负载随之增加。

抗锯齿处理游戏已经合成的画面，可能同时使文字与细节变柔和。关闭附加抗锯齿仍保留游戏自带的抗锯齿。SMAA 使用边缘检测、混合权重、邻域混合三遍，中、高档使用不同搜索及边角处理参数。

帧率档位是上限，保留游戏自身节拍，不解除游戏的 30/60 帧锁。120 档允许无交换间隔的游戏按最高 120 帧/秒呈现；请求 60 Hz 节拍的游戏仍按 60 Hz 运行。实际显示帧率受设备刷新率和运行性能限制。“不限”仅撤掉额外上限。

## 渲染与缓存约定

- 原有 `render_scale` 的布局保持；末尾的 `render_scale_y` 单独表达纵向倍率。宽屏只组合横向倍率，各纹理原有的缩放资格保持有效。
- 逐纹理倍率随创建、线程转发、视图和录像保存。页图片、小图与整屏副本判据按客体尺寸计算，视口及裁剪继续使用 GPU 层已经缩放的实际像素坐标。旧录像的纹理创建操作仍按 1× 解释。
- 游戏渲染完成后，先裁切、翻转并定格，再执行抗锯齿，最后按所选滤镜缩放上屏。每个定格槽保存本帧的处理结果，后续游戏绘制和偏好变化不会改变已冻结的帧。
- 关闭抗锯齿复用原定格纹理，不增加计算处理。原 `nxgal_screenshot` 继续返回未附加抗锯齿的诊断图；`nxgal_screenshot_processed` 返回附加抗锯齿后的、窗口缩放前的图。
- 辅助着色器随现有 helper 链离线编成 metallib。SMAA 首次使用及尺寸变化仍需创建对应 Metal 管线。
- 支持缓冲与着色器语义已更新，旧宿主着色器缓存不能复用。应按当前源码重新生成资源包的着色器缓存与离线库；单独替换 App 后继续使用旧包不构成完整更新。

## 启动工具与验证

启动环境变量优先于系统偏好，便于同一包做可重复对照；Mac 可直接用这些参数：

| 环境变量 | 可选值 |
|---|---|
| `S2A_RES_SCALE` | `0.5`、`0.75`、`1`、`1.5`、`2` |
| `S2A_ANTI_ALIASING` | `None`、`SmaaMedium`、`SmaaHigh`（不带 FXAA：NVIDIA FXAA 3.11 声明里没有授权条款，10-30 去掉；存过的 Fxaa 按无效值清除、回到关闭） |
| `S2A_SCALING_FILTER` | `Bilinear`、`Nearest` |
| `S2A_FPS` | `0` / `off`（不限）、`display`（跟随当前显示器刷新率）、`24`–`1000`（该帧率） |
| `S2A_OUT_SIZE` | `native`（窗口像素，缺省）、`fit`（同 native）、`WxH`（如 `2560x1440`，像素预算） |

```sh
make native-test-ios_settings gfx-test-frame-pacing
make -C graphics/metal "$(pwd)/build/gal/t_aa" "$(pwd)/build/gal/t_present"
build/gal/t_aa
MTL_DEBUG_LAYER=1 MTL_SHADER_VALIDATION=1 build/gal/t_aa
build/gal/t_present
bash tests/graphics_settings/test.sh <真实游戏帧.png> <输出目录>
bash tests/graphics_settings/run_game.sh <改写模块目录> <资源包目录> <本局目录> 0.75 SmaaHigh 30
```
`S2A_FPS` 的三种取值与限制（11-08）：

- 上限只把出图周期**拉长**（周期 = max(游戏交换间隔周期, 1/上限)），不会让锁帧的游戏变快。30/60 帧锁的款选 144 仍是 30/60 帧。
- 唯一因此能超过 60 的，是游戏自己**不锁帧**（交换间隔 0）的款：上限高于 60 时按 1/上限 出图，显示链接进高刷新档（按上限跑，夹到屏幕速率）。
  交换间隔 ≥ 1 的款维持原来的节拍，与上限无关。
- 上限不是整数分之一屏幕速率时（如 165 Hz 屏上选 100），显示链接跑屏幕速率、只数 1/上限 秒一拍；帧间隔取样仍是真实时间。
- 运行中改上限由宿主内部接口 `nvn_fps_set` 完成（`graphics/nvn/gfx/nvn/nvn_fps.c`）；启动环境给错仍然直接退出，运行中给错只拒绝并保留旧值。

出包时的默认值（`s2a_display.tsv`，出包阶段 `pack/stage_caps.sh` 写，只能在 Mac 包里）：

- 请求的 `display` 字段（`pack/jobs/build.py display_env`）：`{"refresh": "144" | "display" | "off", "outSize": "2560x1440" | "native" | "fit"}`。
  Mac 出包经 `S2A_DISPLAY_REFRESH` / `S2A_DISPLAY_OUT` 传进能力清单阶段；Windows 出包机同一份（`pack/orch/stages.py`，`--display-refresh` / `--display-out`）。
- 写出的文件形如 `plat<TAB>macos` 加 `refresh` / `out_size` 两行；宿主 `runtime/src/display_cfg.c` 在装载前读，**只在环境变量未设时**写 `S2A_FPS` / `S2A_OUT_SIZE`。
- 优先级仍是 启动环境 > 玩家设置 > 包内默认。没给这两项就不写文件，产物与原先逐字节相同；这两项进能力清单阶段的键（改分辨率会重出包）。

运行中改（`<文档根>/display.txt`，`runtime/src/display_ctl.c`）：

```
refresh=144        # off / display / 24–1000
out=2560x1440      # native / fit / WxH
fps60=0            # 60 帧表开关（0 / 1）
```

- 每 500 ms 最多读一次（上屏帧回调里判，不动表格写入线程，也不在帧路径上等锁）。写入方应先写 `display.txt.tmp` 再 rename；读侧前后各 stat 一次，中途变了整轮作废。
- 坏行只打黄并保留该键上一次的值；不认识的键忽略（后续版本可以加）。生效变化打一行「显示：…（display.txt）」。
- 文件不在 = 没有运行中改。它不是包内默认值（那是出包阶段写的 `s2a_display.tsv`）：值链仍是 启动环境 > 玩家设置 > 包内默认。
- `out` 改完让窗口壳重摆一次（`s2a_mac_relayout`）；无窗口局 / 没有壳时打黄，下一次布局生效。

`S2A_OUT_SIZE` 的折算规则（Mac，`macos/front_mac.m` 与 `graphics/nvn/gfx/nvn/nvn_present_fit.h pf_out_raster`）：

- `WxH` 是**像素预算**。窗口比例与该预算比例相差 ≤ 1% 时原样使用（16:9 窗口选 `2560x1440` 就是 2560×1440）。
- 比例对不上时按窗口比例取等像素尺寸（如 16:10 窗口 1470×956 上选 `2560x1440` → 2381×1548），层始终铺满视图：
  不比比例摆放会在可画尺寸里留黑边，被满屏判据记成「画面只占 N/M 像素宽」，该局的帧率与能耗读数随之变成未测；拉伸又会被记成变形。
- 每次栅格变化日志一行「出图栅格 WxH（S2A_OUT_SIZE=…，窗口 …）」，检查是否真按预期出图看这一行。
- 只有直连主路径与 Mac 窗口壳生效；iOS 出图层仍是屏幕原生像素。

`test.sh` 从实际 Settings.bundle 读取倍率、抗锯齿和滤镜的全部 40 个组合，经生产 C# 设置入口送到真实 Metal 后端，核对原始图不变、各抗锯齿与滤镜输出有区别。倍率在此测试中只核对配置传递；实际纹理尺寸与场景兼容必须用真实游戏局验证。测试输出、截图与 JSON 均放在指定输出目录，游戏帧不进入源码仓库。

`run_game.sh` 使用当前工作树已构建的宿主，只读游戏资源，为每一局单独创建存档、缓存、录像与存帧目录。它要求游戏实际产生第 60–62 帧，并导出记录的真实尺寸；没有出帧会失败。

`tests/visual/resolution_shader_check.py` 核对真实客体着色器翻译后的 SPIR-V 与支持缓冲布局。当前真实语料包含基线已有的透明测试字段访问及计算状态缺失错误，全库 SPIR-V 检查尚不能全绿；该工具保留失败状态，配对对照用于识别新增错误。

逐纹理倍率、宽屏页判据、整屏副本与录像兼容的真实 Metal 检查见 [resolution_unit](../tests/visual/resolution_unit/README.md)，输入使用已有真实游戏捕获，不生成游戏素材。

## 惊奇 iOS 内存布局

惊奇启动会申请 `0x5b200000` 字节普通堆，原别名优先布局只留 32 MB，无法满足。这里包含 `fix/smbw-ios-heap` 的 `0b3e010d` 修复：`balanced` 使用 56 GB 别名区、6 GB 普通堆及 128 MB 栈，并将窗口最后完整 1 GB 还给 Metal。

`pack/ipa.sh smbw` 默认选择 `balanced`，其他游戏仍选择 `alias`。直接使用 `make ios` 构建惊奇时需要显式传入布局：

```sh
make ios IOS_MODS=<惊奇改写模块目录> IOS_BUNDLE=<包名> IOS_VAMM_LAYOUT=balanced
```

布局写入 App 的 `S2AVammLayout`，同时参与 IPA 缓存键。直接构建的 App 仍需按出包流程复制 `build/gal/ios/gal_helpers` 并签名。开发测试可加 `IOS_AUTOPLAY=1` 编入自动玩家，只有显式传入 `S2A_ROUTE` 或 `S2A_AUTOPLAY=1` 才会自动输入；普通启动不自动按键。
